## 3. Einzelbefunde

### P34 – Vergleich und Schreiben sind nicht atomar

**Ort:** [data-store.js:784](</Users/lukasthielen/Documents/Claude/Assets App/data-store.js:784>) (`commit`, Vergleich vor `setItem`). Ergänzt P1: der geprüfte serielle Konfliktfall funktioniert, das gleichzeitige Schreiben bleibt offen.

**Reproduktion:** Zwei Store-Instanzen teilen einen Speicher. A schreibt zwischen der letzten Prüfung von B und dem Schreiben von B. Der Storage-Adapter stellt diese Reihenfolge deterministisch her:

```js
const st = new MemoryStorage();
const A = Data.createStore(st), B = Data.createStore(st);
const write = st.setItem.bind(st); let once = true;
st.setItem = (k, v) => {
  if (once) { once = false; A.setItem('lt-inflation', '3'); }
  write(k, v);
};
B.setItem('lt-safety', '90');
console.log(JSON.parse(st.getItem(Data.KEY)).forecast.settings);
```

**Erwartet / tatsächlich:** Entweder bleiben Inflation 3 und Sicherheit 90 erhalten, oder einer der beiden Vorgänge scheitert sichtbar. Tatsächlich steht nur `{safetyPercent:90}` im Dokument; Inflation 3 verschwindet ohne `CONFLICT`.

**Ursache:** `getItem` und `setItem` bilden keine gemeinsame Transaktion. Das `storage`-Ereignis repariert einen bereits überschriebenen Stand nicht. Die Web-Storage-Spezifikation verlangt, bei mehreren Agenten keine übergreifende Sperre anzunehmen. Der Nachweis ist ein kontrollierter Adapter-Ablauf, **kein** gemessener gleichzeitiger Browser-Stresstest. [WHATWG Web Storage](https://html.spec.whatwg.org/multipage/webstorage.html)

**Behebung:** Alle Schreibpfade durch eine tatsächlich fensterübergreifende Serialisierung beziehungsweise transaktionale Speicherung führen. Web Locks benötigt einen tragfähigen Fallback für `file://`; alternativ eine dokumentierte Single-Writer-Lösung oder IndexedDB-Transaktion. Ein zweiter Vergleich vor dem Schreiben verkleinert nur das Zeitfenster.

**Regression:** `concurrent commits cannot overwrite an intervening write`: kontrollierte Zwischenoperation und anschließend Browser-Test mit zwei unabhängigen Fenstern; keine erfolgreiche Änderung darf unbemerkt verschwinden.

**Erwartet / tatsächlich:** Veralteter Abruf wird verworfen oder mit dem neuen Instrument wiederholt. ## 5. Offene fachliche Entscheidungen mit Empfehlung

1. **Wie sollen mehrdeutige Altgehälter migriert werden?** Empfehlung: geführte Zuordnung mit unverändertem Original und einer Vorschau des Gesamtbudgets; keine still zusätzlich erzeugten Einnahmen. Name/Betrag dienen nur als Vorschlag. Betrifft P35.
2. **Darf die Teilzeitmigration den alten Beginn verändern?** Empfehlung: bestehende exakte Zeitgrenzen erhalten, bis eine konkrete Umstellung bestätigt wurde; automatische Mehrheitszuordnung allein ist für produktive Planung ungeeignet. Betrifft P36.
3. **Welche Bedeutung haben Budgetbeträge über die Zeit?** Empfehlung: Einkommen und Ausgaben in heutiger Kaufkraft, Sparraten mit der gesonderten nominalen Steigerung; alle Deltas dann mit konsistenten Einheiten rechnen. Bei bewusst nominal konstanten Gehältern muss dies ausdrücklich auswählbar sein und überall gelten. Betrifft P45.
4. **Wie wird eine spätere Arbeitsaufnahme aus heute 0 % modelliert?** Bei 0 % liefert der heutige Gehaltsbezug keine Vollzeitbasis. Empfehlung: künftiges Netto/Brutto oder ein Vollzeitreferenzgehalt verlangen, sobald Arbeitszeit aus 0 steigt; einen Hinweis zeigen, statt eine ungeprüfte Gehaltsannahme abzuleiten. Dieser Fall wird hier als Modellentscheidung behandelt, nicht als zusätzlicher reproduzierter Fehler.
5. **Was passiert nach einem nicht finanzierbaren Beitrag?** Empfehlung: tatsächlich finanzierten Teil buchen, Fehlbetrag sichtbar ausweisen und Simulation weiterführen; keine hypothetischen Eigenbeiträge/Zulagen in den Vermögenspfad aufnehmen. Ob der persönliche Sparplan zusätzlich als „gestoppt“ weiterläuft, ist eine Szenarioentscheidung. Betrifft P44.
6. **Welche EM-Daten sollen Nutzer eingeben?** Empfehlung: frühere Zugangsfaktoren/Punktanteile oder einen bestätigten Folgerentenbetrag erfassen; den automatischen Übergang bis dahin sichtbar als unvollständig behandeln. Betrifft P47.
7. **Sind ungefähre historische Bewertungen erwünscht?** Empfehlung: standardmäßig exakter Monats-FX oder Monat unverändert; Näherungen nur gekennzeichnet und ausdrücklich gewählt. Betrifft P39. Bei Januar-Bonusgrenzfällen analog keine still behauptete Berechtigung, sondern Datum oder Berechtigungsangabe erfragen (P49).

Technisch sollten zuerst P34–P38 zum Schutz vorhandener Daten und anschließend P40–P47 für den Rechenkern bearbeitet werden. Für einen Folge-Review sollte Claude pro Befund den neuen Regressionstest, die unabhängig hergeleiteten Sollwerte und gegebenenfalls die bestätigte Modellentscheidung angeben. Die iOS-Spezifikation sollte erst nach diesen Entscheidungen an das konsolidierte fachliche Modell angepasst werden.
